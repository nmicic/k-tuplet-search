# KT Search Pipeline

Status: current implementation overview. Older phase labels in commit history
refer to development milestones; the production GPU and CPU paths are now
implemented.

## Overview

The pipeline mirrors the filter-then-prove architecture from
`cunningham-chain-search/`, adapted to additive k-tuplet shifts.

1. Resolve an admissible pattern `B = {b_0, ..., b_{k-1}}`.
2. Build admissible wheel offsets modulo the selected primorial or wheel expression.
3. Sweep candidate bases through the CUDA forbidden-residue cascade.
4. Prove surviving candidates on the host with GMP/BPSW for all `n + b_i`.
5. Persist confirmed hits to JSONL and optional user output files.

The speed comes from avoiding expensive primality work for almost all
candidates.

## Forbidden Residues

For a k-tuplet pattern `B` and prime `q`:

```text
forbidden_r[j] = (q - (b_j % q)) % q    for j = 0..k-1
```

A candidate base `n` is killed by `q` iff `n % q` is in that deduplicated
forbidden set. Unlike Cunningham chains, no modular inverse or depth-dependent
ladder is needed.

Implemented in:

- `src/common/ktuplet_pattern.c` / `.h`
- `gp/kt_lib_v1.gp`
- `src/cuda/kt_filter_v8.cu`
- `src/cpu/kt_gmp_v1.c`

## Engine Layers

| Layer | Implementation | Notes |
|---|---|---|
| Pattern catalog | `src/common/ktuplet_pattern.c` | 97 engine patterns across `k=3..28` |
| Wheel builder | `src/cuda/kt_wheel.c` | Supports production wheels through `47#` and quotient expressions such as `47#/31/17` |
| GPU filter | `src/cuda/kt_filter_v8.cu` | L2, ext-L2, line-sieve, Fermat-2 stages |
| Host prover | `src/common/kt_verify.c` + GMP | Verifies every member of a survivor |
| Record loader | `src/cuda/kt_records.c` | Reads `known/records.json` and `tools/records_manifest.tsv` |
| Persistence | `src/cuda/kt_novel_record.c` | fsync'd `novel_records*.jsonl` output |
| CPU reference | `src/cpu/kt_gmp_v1.c` | Slower independent engine for low-volume checks |

## Candidate Parameterization

The CUDA engine walks wheel-modulus-aligned candidate bases:

```text
n = tile * wheel_modulus + wheel_offset
```

where `wheel_offset` is one of the admissible residues for the active pattern.
Prefix modes and prefix lanes restrict the tile interval for validation,
distributed search, and checkpoint/resume.

## Pattern Scope

The CUDA engine catalog (`KT_PATTERNS[]`) is the full search catalog:

- `97` patterns total
- `k=3..28`
- reflections included as separate search directions
- generated by `tools/gen_pattern_header.py` from `tools/patterns/catalog/*.json`

The GP/PARI toolkit (`KT_CATALOG`) intentionally remains smaller: 25 planning
and record-analysis patterns for `k=5,7,9,16..24`.

Norman Luhn's `ktpatt_hl.php` page is the authoritative reference for patterns
and Hardy-Littlewood constants. Local enumeration tools are convenience code,
not a replacement for that reference.

## Record Replay and Search Targets

`known/records.json` contains 227 replay records across `k=16..21`. The primary
GPU correctness gate is `--validate-known`, which narrows each replay to a
known prefix and proves that the engine can reproduce known records.

Practical campaign examples in this repo focus on:

| Use | k | Notes |
|---|---|---|
| Regression replay | 16..21 | Known records from Luhn history pages |
| Record-search examples | 19, 20, 21 | Current high-k published-record tiers |
| Exploratory frontier | 22..28 | Engine-supported patterns; no new record claimed here |

The longevity scripts represent random sampling and stability testing, not an
exhaustive search of the 100-bit ranges.

## Planning Tools

Use GP/PARI or the Python/C pattern tools for campaign planning:

```gp
\r gp/kt_lib_v1.gp

\\ How many prefix bits to fix for a 60-second GPU campaign?
kt_prefix_bits_for_budget(90, 19, 50e9, 60)

\\ Sieve survival rate for k=19 after filtering primes <= 97
kt_sieve_survival_rate(kt_pattern_by_name("KT19_P0")[3], 97)
```

For the full engine catalog, inspect:

```bash
./src/cuda/kt_filter_v8 --list-patterns
```

The output lists the pattern name accepted by `--pattern`, tuple length,
diameter, and offsets. See [`CUDA_CLI_REFERENCE.md`](CUDA_CLI_REFERENCE.md)
for the complete CUDA command-line reference.
