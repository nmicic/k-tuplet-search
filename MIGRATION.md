# MIGRATION.md — Cunningham Chain to k-Tuplet: Concept Analogies

This document maps every major concept from the CC18 search engine
(`cunningham-chain-search/`) to its k-tuplet analog in this project.
Intended as a reference for porting Phase 2 (CPU engine) and Phase 3 (GPU kernel).

---

## Core Mathematical Difference

| Aspect | Cunningham Chain (CC) | k-Tuplet (KT) |
|--------|----------------------|---------------|
| Structure | `{p, 2p+1, 4p+3, ..., 2^{k-1}p + (2^{k-1}-1)}` | `{n+b_0, n+b_1, ..., n+b_{k-1}}` |
| Growth law | Multiplicative: `p_{i+1} = 2p_i + 1` | Additive: fixed shifts `b_i` |
| Chain root | Smallest prime where `(p-1)/2` is not prime | Smallest `n` with all members prime |
| Pattern shape | Determined by kind (1st or 2nd) — unique | k admissible patterns per k (2 to 4) |
| H(k) (diameter) | `2^{k-1} - 1` grows exponentially | Sub-linear: H(19)=76, H(21)=84 |

## Forbidden-Residue Formula

This is the central filter difference.

### CC (first kind), prime q, chain depth k

```
forbidden_r[i] = (2^{-i} - 1) mod q    for i = 0..k-1
```

Requires `mod_inverse(2, q)` and `pow(inv2, i, q)` — depth-dependent.

### k-Tuplet, prime q, pattern B = {b_0,...,b_{k-1}}

```
forbidden_r[i] = ((q - (b_i % q)) % q)    for i = 0..k-1
```

No modular inverse. No chain depth dimension. Just `(-b_i) mod q`.

**Implementation consequence:** The GPU sieve inner loop simplifies dramatically.
One subtraction and one modulo per offset, vs. a modular exponentiation ladder.

## Search Pipeline Analogy

| Phase | CC18 (cunningham-chain-search) | KT (this project) |
|-------|-------------------------------|-------------------|
| Lattice | CRT bases satisfying forbidden-residue constraints | Same — admissible residues mod primorial |
| Wheel | `n = k * primorial + base` form | `n = k * primorial + base` form |
| GPU filter | Depth-i forbidden residue check for many small primes | Forbidden-residue check per offset for many small primes |
| CPU confirm | `isprime` on chain root + chain walk | `isprime` on all k members at base n |
| Verification | `cc_chain_verify(p)` in GP | `kt_verify_tuplet(n, pat)` in GP |

## GPU Kernel Changes (Phase 3)

The CC18 GPU kernel (`cc18_filter_cuda_CpC_v13.cu`) uses a 3-stage depth filter:

```c
// CC: for each prime q, forbidden residue at depth i requires modular inverse
uint32_t forbidden_i = (mod_inverse(pow2_mod_q(i), q) - 1 + q) % q;
if (n % q == forbidden_i) { reject; }
```

The KT GPU kernel replaces this with:

```c
// KT: for each prime q, forbidden residue for offset b_j is just (-b_j) mod q
for (int j = 0; j < k; j++) {
    uint32_t forbidden_j = (q - (offsets[j] % q)) % q;
    if (n % q == forbidden_j) { reject; break; }
}
```

**Key differences to propagate:**
- No `pow2_mod_q()` table needed.
- No chain-depth loop — replaced by offset loop (length k, not depth).
- Multiple patterns per k — kernel parameterized on pattern index.
- Survivor condition: ALL offsets survive, not one depth.
- Throughput estimate: similar to CC18 (~50-65G candidates/sec on RTX 4090).

## Open Questions for Phase 2/3

1. **Multi-pattern parallelism**: the CC18 engine handles one chain kind at a time;
   the KT engine should handle multiple patterns for the same k simultaneously
   (4 patterns for k=17 and k=19 — run all 4 in one GPU pass?).

2. **Wheel density**: KT survival rates are similar to CC18 at the same k;
   see `kt_sieve_survival_rate()` for estimates.

3. **Candidate form**: CC18 uses `n = k*M + base`; KT will use the same form
   with `M = primorial` and `base` from the admissible set.

4. **Pattern selection**: for records, only k ∈ {17, 19, 21} matter.
   The GPU engine should be parameterized at compile time for a given (k, pattern_id).
